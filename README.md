# MakeMeSmall

**https://makemesmall.vercel.app**

Пакетное сжатие картинок в браузере. Кидаешь папку — получаешь ZIP со сжатыми файлами.
Ничего не загружается на сервер: всё считается локально в Web Workers.

## Деплой

Проект подключён к Vercel (`hellowrld/makemesmall`), production-ветка —
`claude/image-compressor-p00xqc`. Каждый push в неё пересобирается и выкатывается
автоматически. Сборка занимает ~3 с, на выходе статика без бэкенда.

## Запуск

```bash
npm install
npm run dev      # http://localhost:5173
npm run build    # статика в dist/ — кладётся на любой хостинг
```

## Как подбирается качество

Качество ищется для каждой картинки отдельно. Ключевых решений три, и все три
выведены из замеров на 12-мегапиксельных фото, а не из общих соображений.

**1. Порог качества — относительный, не абсолютный.** Первая версия требовала
фиксированный SSIM (0.985–0.9985). Это не работает: шумное фото не достигает 0.99
ни при каком разумном размере, а гладкое берёт этот порог уже на quality 0.4. На
детализированных фото поиск упирался в потолок и сжатие давало **−1%**. Теперь
меряется потеря *относительно эталонного кодирования той же картинки* (quality
0.92): берётся минимальное качество, при котором SSIM не ниже `эталон − Δ`.

| Режим | Δ | Смысл |
|---|---|---|
| Качество | 0.010 | почти неотличимо от эталона |
| Оптимально | 0.025 | рабочий баланс |
| Компактно | 0.050 | заметно меньше файл |

**2. Замер идёт на нативных тайлах, а не на превью.** Раньше SSIM считался на
уменьшенной до 480 px копии. Даунскейл убивает высокие частоты — то есть именно
те артефакты, за которыми надо следить, — и превью врёт в обе стороны: на одной
картинке показывает 0.985 там, где на полном кадре 0.973, на другой 0.985 против
0.9998. Теперь берутся 4 самых детализированных тайла 320×320 в нативном
разрешении. Замер на них совпадает с полнокадровым SSIM с точностью до третьего
знака (Δsheet 0.0764 против Δtrue 0.0757) и при этом в 25 раз быстрее полного
кодирования.

**3. Два жёстких ограничителя, оба измеренные:**

- *Обрыв JPEG.* Между quality 0.80 и 0.85 файл прибавляет ~55% при росте SSIM на
  0.01 — стабильно на всех тестовых фото. Потолок для JPEG выставлен на 0.82: за
  этой границей байты покупают ничто.
- *Пол для графики.* SSIM почти не штрафует замыленный текст, поэтому на
  скриншотах метрика готова уронить качество до 0.5. Доля «плоских» 8×8 блоков
  чисто разделяет контент (0.83 у скриншота против 0.014–0.031 у фото), и для
  графики качество не опускается ниже 0.85.

Плюс инвариант поверх всего: **результат никогда не больше исходника**. Если
пережатие дало прирост, в архив идёт оригинал, строка помечается «уже оптимально».

## Результаты

51 фото по 12 Мп, 113 МБ, Chromium, 4 воркера:

| Режим | Было → стало | Время |
|---|---|---|
| WebP · Качество | 113 МБ → 58.8 МБ (−48%) | 31 с |
| WebP · Оптимально | 113 МБ → 42.2 МБ (−63%) | 30 с |
| WebP · Компактно | 113 МБ → 24.8 МБ (−78%) | 27 с |
| JPEG · Оптимально | 113 МБ → 63.5 МБ (−44%) | 9 с |

Предыдущая версия на том же наборе давала −1% (WebP) и −0% (JPEG).

Проверка качества независимая: файлы берутся **из скачанного архива** и
сравниваются с оригиналами. Все 36 выходов сохраняют исходное разрешение, худший
SSIM по всем режимам — 0.925 (Компактно на самом шумном кадре), в режиме
Оптимально 0.951–0.999.

## Настройки

| Контрол | Значения |
|---|---|
| Режим | Качество / Оптимально / Компактно |
| Формат | WebP / JPEG / Как есть |

Смена контрола отменяет текущий прогон и пережимает всё заново из оригиналов.
Тема — кнопка в правом верхнем углу: как в системе / светлая / тёмная, выбор
запоминается.

## Ограничения

- **AVIF не поддерживается.** `OffscreenCanvas.convertToBlob({type:'image/avif'})`
  в Chromium возвращает PNG — проверено, не гипотеза. Кодировать AVIF в браузере
  сейчас нечем.
- **PNG убран из выбора формата.** Canvas не умеет квантовать палитру, поэтому
  PNG→PNG почти всегда возвращает оригинал, а JPEG→PNG раздувает файл в 5-7 раз.
  Кнопка создавала ложные ожидания. PNG-источники в режиме «Как есть» остаются
  PNG и честно показывают «уже оптимально»; для скриншотов берите WebP — он даёт
  −38% при SSIM 0.999.
- **Кодек — браузерный.** mozjpeg/oxipng через WASM дали бы ещё 5–10%, но это
  +2 МБ бандла и втрое медленнее.
- **HEIC** не декодируется вне Safari — такие файлы помечаются ошибкой.
- **ZIP без ZIP64**: архив больше 4 ГБ не соберётся (выдаст ошибку, а не битый файл).
- WebP-кодирование 12 Мп занимает ~1 с на ядро — это потолок скорости, поиск
  качества на его фоне стоит 0.3 с.

## Структура

```
src/main.ts    UI, drag&drop с обходом папок, состояние, сборка архива
src/worker.ts  декод, поиск качества по SSIM на тайлах, энкод, CRC32
src/pool.ts    пул воркеров с очередью и отменой
src/zip.ts     store-only ZIP + CRC32
src/style.css  стили, светлая и тёмная тема
```
